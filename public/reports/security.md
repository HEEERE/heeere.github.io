# RAISE — 技术报告

多智能体级联污染与防御可视化平台

> 根据项目文档与作品集说明整理的设计与实现说明。验证方法为复核建议，流程演示采用本地预设数据；本报告不包含原始评测记录或独立复现结论。

## 系统实现与交付

- **Ledger / 版本化来源**：不可变数据版本与追加状态记录，保留派生关系及动作依据。
- **双图 / RAISE 分工**：紧图提出候选，保守图作安全判断，独立检查器复核残余路径。
- **Gateway / 执行边界**：统一动作闸门与状态修复，连接隔离、限制保留和干净重放。

## 问题与边界

RAISE 是多智能体级联污染与防御的研究平台，连接攻击仿真、防御执行、来源追踪与运行观察。本文根据项目 README 和对应源码模块整理，仅展示机制和流程，不展示具体实验数据。

## 版本化账本与动作闸门

MessageBus 连接事件流与 ProvenanceLedger。数据对象以不可变版本保存，后续变化追加到状态记录。ActionGateway 统一检查受保护动作的权限、参数来源、作用范围和执行模式；检测模型只能提供否决证据，不能直接产生授权。执行模式在闸门构造时固定，检查与执行之间的快照变化会使旧依据失效。

## 双图分析与独立检查

RAISE 将分析分为保守图与紧图。紧图提出候选修复或保留方案，保守图承担安全判断；独立 checker 在干预后的保守图上重新检查残余污染路径。UNKNOWN 表示证据、范围或预算不足，UNSATISFIABLE 表示已证明没有可用切断方案，两者不混用。

## 状态修复与界面

状态控制器在复核后提交失效、隔离与限制保留。保留版本仍带强制标签，不能充当高影响动作的授权依据；恢复从干净输入创建新版本。FastAPI 与 WebSocket 提供经过裁剪的运行投影，React 界面连接策略编辑、来源图、事件追踪与回放。

## 设计取舍

保守图倾向保留可能的污染关系，因此可能扩大干预范围；紧图有助于提出代价更小的候选方案，但不能独立证明安全。独立检查、版本快照和动作队列增加了工程复杂度，换来可重查的执行依据与状态边界。

## 个人贡献

- 构建 MessageBus 与版本化 ProvenanceLedger，记录消息、记忆、检索和动作参数的来源关系及追加式状态变化。
- 实现统一 ActionGateway，检查动作权限、参数来源、作用范围与执行模式；检测模型的证据只能否决，不能直接授权。
- 实现 conservative / tight 双图分工：紧图提出候选修复方案，保守图承担安全判断与独立复核。
- 通过独立 checker 检查残余污染路径，再提交失效、隔离和限制保留；从干净输入重放，避免重新激活已失效版本。
- 提供 FastAPI、WebSocket 运行投影、React 操作界面与 Trace Replay，连接策略配置、过程观察和机制验证。

## 系统流程

Provenance → ActionGateway → Dual Graph → Independent Check → Repair → Clean Replay

## 验证方法

- 来源：核对版本不可变、追加式状态变化、运行隔离与派生关系。
- 闸门：检查未知来源、快照变化、异常和受限执行模式下的拒绝路径。
- 修复：核对双图分工、独立检查、限制标签与干净重放；失效版本不能重新激活。
